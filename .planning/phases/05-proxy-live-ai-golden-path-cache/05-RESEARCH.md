## Summary

Phase 5 builds the live AI data layer: a Vercel serverless proxy (`api/live.ts`) that calls Anthropic with `web_search` and returns typed `LiveDataResponse<T>` objects, a bundled golden-path JSON file (`data/golden-path/demo-results.json`) that serves as the dual offline fallback (client-bundled and proxy-embedded), and a capture script (`scripts/capture-golden-path.ts`) that snapshots real proxy output before pitch day.

The primary integration risk is LLM output parsing: web_search turns return a content-block array with prose, citations, and tool results — not JSON. Every endpoint must force JSON output via prompt, extract from a fenced block, and validate against the item shapes before returning. Any parse failure immediately returns the golden-path JSON with `fromCache: true`. This is the LIVE-04 guarantee.

The secondary risk is the client timeout budget. With `max_uses: 3`, a web_search call realistically takes 8–20 seconds. If the client hard-bails at 7s the live "wow moment" (D-04) never fires. The planner must set the client timeout at 20s for the live path, reserving 7s only as the fallback-trigger for the instant-cache path when the proxy is unreachable (network error, not just slow).

**Primary recommendation:** Use `claude-sonnet-4-6` (the only current model explicitly confirmed by Anthropic docs to support both `web_search_20250305` and `web_search_20260209`). Use the `@anthropic-ai/sdk` for the proxy — the SDK earns its keep parsing the content-block array response shape. Validate outputs with hand-rolled type guards (three simple item shapes, no new dependency needed for validation, though `zod` is available on npm at 4.4.3 if the planner prefers schema-first validation).

### Pattern 1: Vercel Serverless Handler (follow api/health.ts exactly)

**What:** `export default function handler(req, res)` typed via `@vercel/node`. Imports from `../shared/types`. Runs under `vercel dev` locally, deployed as a Vercel function.

**Example:**
```typescript
// Source: api/health.ts (confirmed working pattern)
import type { VercelRequest, VercelResponse } from '@vercel/node';
import type { LiveDataResponse, LiveDataRequest } from '../shared/types';
import Anthropic from '@anthropic-ai/sdk';
import goldenPath from '../data/golden-path/demo-results.json';

const client = new Anthropic(); // reads ANTHROPIC_API_KEY from process.env

export default async function handler(req: VercelRequest, res: VercelResponse): Promise<void> {
  if (req.method !== 'POST') {
    res.status(405).json({ error: 'Method not allowed' });
    return;
  }
  const { category, cityName, profession, age } = req.body as LiveDataRequest;
  try {
    const raw = await callAnthropicWithSearch(category, cityName, profession);
    const items = parseAndValidate(category, raw);
    const response: LiveDataResponse = { category, cityName, fromCache: false, items };
    res.status(200).json(response);
  } catch {
    // SC5: Anthropic failed but proxy reachable → serve golden-path
    const fallback = (goldenPath as Record<string, Record<string, unknown>>)[category]?.[cityName];
    const response: LiveDataResponse = {
      category, cityName, fromCache: true,
      items: fallback ?? []
    };
    res.status(200).json(response);
  }
}
```

### Pattern 2: web_search Tool Call (via SDK)

**What:** Call Anthropic SDK `messages.create` with `web_search_20250305` tool. Response is a content-block array; extract the final text block(s) concatenated together.

**Tool configuration:**
```typescript
// Source: [VERIFIED: platform.claude.com/docs/en/docs/build-with-claude/tool-use/web-search-tool]
{
  type: "web_search_20250305",  // stable, no code execution dep, model-agnostic
  name: "web_search",
  max_uses: 3,                  // bounds cost + latency; adequate for structured listing queries
  user_location: {              // localizes results to target city
    type: "approximate",
    city: cityName,             // the full city.name, e.g. "Austin, TX"
    country: "US"               // ISO alpha-2; derive from cityName suffix ("Lisbon, Portugal" -> "PT") — see "Complete api/live.ts skeleton"
  }
}
```

**Model:** `claude-sonnet-4-6` [CITED: platform.claude.com/docs/en/about-claude/models/overview]

**Response parsing:**
```typescript
// Source: [CITED: platform.claude.com/docs/en/docs/build-with-claude/tool-use/web-search-tool]
// Response is content_block[]. Text blocks after tool_result blocks contain the final answer.
function extractText(response: Anthropic.Message): string {
  return response.content
    .filter(b => b.type === 'text')
    .map(b => (b as Anthropic.TextBlock).text)
    .join('');
}

function extractJSON(text: string): unknown {
  // LLM outputs ```json ... ``` or bare JSON
  const fenced = text.match(/```(?:json)?\s*([\s\S]*?)```/);
  const raw = fenced ? fenced[1].trim() : text.trim();
  return JSON.parse(raw); // throws on malformed → caught → golden-path fallback
}
```

### Pattern 4: LLM Output Validation (type guards)

**What:** After extracting JSON from the response text, validate it against the expected item shape before returning to the client. On failure, throw (caught by the outer try/catch → golden-path fallback).

**Item shapes (inferred from PotentialApp.jsx renderer + D-10):**
```typescript
// Jobs: rendered as job.title, job.company, job.salary, job.desc, job.source (D-10, no url anchor)
interface JobListing {
  title: string;
  company: string;
  salary?: string;     // "$90K–$120K/yr" or "Not listed"
  desc?: string;
  source: string;      // "Indeed" | "LinkedIn" | "ZipRecruiter" etc — D-10 renders this as text
}

// Housing: rendered as h.name|h.address|h.neighborhood, h.price, h.beds, h.sqft, h.feature, h.source
interface HousingListing {
  name?: string;
  address?: string;
  neighborhood?: string;
  price: string;       // "$1,800/mo" or "$420,000"
  beds: string;        // "2BR" | "3BR"
  sqft?: string;
  feature?: string;
  source: string;      // "Zillow" | "Realtor" | "Idealista" etc — D-10
}

// dayinlife: rendered as a string via AIList → renderItem
// items is a string (narrative), not an array
type DayInLifeNarrative = string;
```

**Validation guards (no zod needed):**
```typescript
function isJobListing(x: unknown): x is JobListing {
  return typeof x === 'object' && x !== null
    && typeof (x as JobListing).title === 'string'
    && typeof (x as JobListing).company === 'string'
    && typeof (x as JobListing).source === 'string';
}

function validateItems(category: LiveCategory, raw: unknown): unknown {
  if (category === 'dayinlife') {
    if (typeof raw !== 'string') throw new Error('dayinlife must be string');
    return raw;
  }
  if (!Array.isArray(raw)) throw new Error('expected array');
  if (category === 'jobs') {
    if (!raw.every(isJobListing)) throw new Error('invalid job shape');
    return raw;
  }
  if (category === 'housing_rent' || category === 'housing_buy') {
    if (!raw.every(isHousingListing)) throw new Error('invalid housing shape');
    return raw;
  }
  throw new Error(`unknown category: ${category}`);
}
```

### Anti-Patterns to Avoid

- **Calling Anthropic from the client** — CORS block + key exposure. Proxy-only. (existing pattern already wrong; Phase 5 fixes it)
- **`url` as `<a>` anchor** — D-10 forbids it. `ItemCard` currently renders `url` as "View listing ↗" anchor (PotentialApp.jsx lines ~213-221). Phase 5 must remove this anchor; render `source` string instead.
- **Expand-trigger for live fetch** — current `Section.onClick` calls `fetchCityAI`. D-04 requires an explicit "Pull live data" button instead. The planner must replace the trigger, not just add a button.
- **Image URLs in golden-path cards** — `ItemCard` renders `image` prop from remote URLs. When hotspot is dead those images 404-silently (the `onError` hides them). Golden-path prompts should NOT include `image` fields; if included, they produce blank image areas offline. Omit `image` from golden-path item shapes entirely.
- **7s client timeout for the live path** — at `max_uses: 3`, web_search realistically takes 8–20s. A 7s client timeout means the live path NEVER completes and judges always see the cache — defeating D-04. Use 20s for the live try; reserve instant-fail (AbortSignal immediate on network error) for SC4.
- **Importing the golden-path JSON without `resolveJsonModule`** — current tsconfig.json does NOT have `resolveJsonModule` and uses `"moduleResolution": "bundler"`. In TypeScript 5+ with `bundler` moduleResolution, JSON imports require `resolveJsonModule: true`. Must be added to tsconfig.json before `api/live.ts` can statically import the JSON. Vite handles JSON natively for `src/`; only the `api/` TypeScript compilation needs the flag.

## Model Choice: claude-sonnet-4-6 (Recommended)

**Decision basis:**

The `web_search_20260209` doc explicitly lists supported models: `claude-opus-4-8`, `claude-opus-4-7`, `claude-opus-4-6`, `claude-sonnet-4-6`. Haiku `4.5` is **absent from this list**. The older `web_search_20250305` lists no explicit models but remains available. [CITED: platform.claude.com/docs/en/docs/build-with-claude/tool-use/web-search-tool]

- **`claude-haiku-4-5-20251001`** — web_search support status is `[ASSUMED]` (not confirmed in Anthropic's official model-support documentation; multiple authoritative pages do not list it). Do NOT use without first verifying in the Claude Console.
- **`claude-sonnet-4-6`** — confirmed `web_search` support, confirmed in `web_search_20260209` model list. `$3/MTok input, $15/MTok output`. For a demo with `max_uses:3`, total cost per live request is ~$0.03–0.08 (3 search fees at $0.03 total + token costs). The cost delta vs Haiku (if Haiku even works) is ~$0.02–0.04 per click — immaterial at demo scale.

**Recommendation: use `claude-sonnet-4-6`.** The quality difference for producing parseable structured listing JSON matters more than token cost at this scale. Haiku may be faster but its web_search support is not confirmed.

**Tool version: `web_search_20250305`** — simpler (no code execution dependency), stable, adequate for structured listing queries. [CITED: platform.claude.com/docs/en/docs/build-with-claude/tool-use/web-search-tool]

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Anthropic API client + content-block parsing | Custom fetch wrapper | `@anthropic-ai/sdk` | Content-block array response (text + server_tool_use + web_search_tool_result blocks) + `pause_turn` stop reason are fiddly to parse manually; SDK handles these cleanly |
| LLM-output schema validation | Custom schema DSL | Type guards OR `zod` | Three fixed shapes; hand-rolled guards are 15 lines each and testable in vitest without a dep |
| Offline fallback persistence | localStorage/IndexedDB | Static JSON import in Vite bundle | localStorage requires a page load to write; bundled JSON is synchronous and survives airplane mode with zero code |

**Key insight:** The golden-path fallback is not a cache — it is a static JSON file committed to the repo and bundled into the Vite build at compile time. It has zero runtime dependencies. Do not implement it as a writable cache or sessionStorage entry.

## Timeout Budget (D-02 Resolution)

| Path | Recommended timeout | Rationale |
|------|---------------------|-----------|
| Client fetch → proxy | 20s | web_search at `max_uses:3` realistically takes 8–20s including token generation. 7s consistently aborts live calls, defeating D-04. |
| Proxy → Anthropic SDK | 25s (let the function natural-timeout) | Vercel Hobby: 60s max (300s with Fluid Compute). Function can wait the full call. |
| Client fallback trigger | Immediate on `AbortError` or `catch` | Network errors abort immediately; the 20s timeout only fires if the connection hangs. |

D-02's "~7s budget" should be interpreted as: the ABORT SIGNAL fires at 20s (live wow moment budget), but if the proxy is UNREACHABLE (connection refused / fetch throws before any bytes) the catch fires instantly — effectively 0s — and the golden-path cache renders without any wait. The 7s budget is a reasonable starting point for "slow hotspot response with no proxy" timeout, but should not be applied as an AbortSignal deadline for the live-proxy path.

```json
    "Lisbon, Portugal": [ ... ]

  "dayinlife": {
    "Austin, TX": "It's 7am and the September sun...",
    "Lisbon, Portugal": "The Tagus gleams through the kitchen window..."
  }
}
```

**City keys are the FULL `city.name` string** ("Austin, TX" / "Lisbon, Portugal" — confirmed in shared/data/cities.ts), NOT bare tokens. The proxy and client both look up `goldenPath[category][city.name]`, so bare-token keys would resolve to `undefined → []` on every offline fallback and void SC4/SC5/LIVE-04. Both `api/live.ts` and `src/` import this file (D-01 single source). Vite handles JSON imports natively in `src/`. The `api/` TypeScript compilation requires `resolveJsonModule: true` in tsconfig.json.

### Capture script: `scripts/capture-golden-path.ts`

**Approach:** The script calls the local Vercel dev proxy (`http://localhost:3000/api/live`) for each category × city combination in sequence, collects the responses, and writes the merged result to `data/golden-path/demo-results.json`.

**Pre-requisites before running:**
1. `ANTHROPIC_API_KEY` set in `.env` (or Vercel env)
2. web_search enabled in Anthropic Console (org admin setting) — see Open Questions
3. Demo persona finalized (D-06 open dependency)
4. `npm run dev:full` (vercel dev) running in a separate terminal

**Script outline:**
```typescript
// scripts/capture-golden-path.ts
// Run: npx tsx scripts/capture-golden-path.ts
// Requires: vercel dev running on localhost:3000

const DEMO_PROFILE = { profession: 'Software Engineer', age: 28, housing: 'rent' }; // TBD from demo script
const CITIES = ['Austin, TX', 'Lisbon, Portugal']; // full city.name strings — the exact golden-path keys (read these from demo-profile.json in the real script)
const CATEGORIES = ['jobs', 'housing_rent', 'dayinlife'] as const;

async function capture() {
  const result: Record<string, Record<string, unknown>> = {};
  for (const cat of CATEGORIES) {
    result[cat] = {};
    for (const city of CITIES) {
      const res = await fetch('http://localhost:3000/api/live', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ category: cat, cityName: city, profession: DEMO_PROFILE.profession }),
      });
      const data = await res.json() as { items: unknown; fromCache: boolean };
      if (data.fromCache) throw new Error(`Got cached data for ${city}/${cat} — check API key + web_search enabled`);
      result[cat][city] = data.items;
    }
  }
  // write result to data/golden-path/demo-results.json
  fs.writeFileSync('./data/golden-path/demo-results.json', JSON.stringify(result, null, 2));
}
```

**Critical guard:** The script throws if `fromCache: true` is returned (means the proxy fell back; snapshot would be stale placeholder data). Only write when all responses are `fromCache: false`.

## Common Pitfalls

### Pitfall 1: Haiku as the model (unconfirmed web_search support)
**What goes wrong:** Deployment with `claude-haiku-4-5-20251001` and `web_search_20250305` may result in the model not performing searches, returning stale training-data listings instead of real current ones.
**Why it happens:** Haiku 4.5 is NOT listed in Anthropic's official web_search supported-models documentation as of 2026-06-03.
**How to avoid:** Use `claude-sonnet-4-6` (confirmed). If Haiku is desired for cost, test explicitly with a web_search call and verify the `server_tool_use.web_search_requests` count in the usage field is > 0.

### Pitfall 2: 7s AbortSignal killing the live "wow moment"
**What goes wrong:** Client bails after 7s; every on-stage live click shows the cache; D-04 never demonstrates real-time data.
**Why it happens:** web_search calls realistically take 8–20s. A 7s abort is shorter than the typical web_search round-trip.
**How to avoid:** Set `AbortController` timeout to 20s for the live path. Network errors (proxy unreachable) abort immediately regardless of timeout value.

### Pitfall 3: `url` rendered as anchor (D-10 violation)
**What goes wrong:** Competition rules disallow clickable links on screen; a judge could click. Also kills the see-not-click narrative.
**Why it happens:** `ItemCard` in PotentialApp.jsx currently renders a `url` prop as `<a>View listing ↗</a>` (lines ~213-221). Prompts that return `url` fields will render them unless the card is modified.
**How to avoid:** Remove the `<a>` block from `ItemCard`. Prompts must NOT request a `url` field. Add a `source` field (site name as text) instead. `url` may be stored in the data for future use but never rendered. Note: Anthropic's web-search-tool docs require attribution when displaying API outputs to end users — rendering the source name as text (e.g. "Indeed", "Idealista") satisfies this requirement; D-10 forbids the link, not the attribution.

### Pitfall 4: Image URLs in golden-path breaking D-08 "identical" offline
**What goes wrong:** `ItemCard` renders `image` from a remote URL. When hotspot is dead, images 404-silently (handled by `onError` to hide) — but this means the cached panel LOOKS slightly different from the live panel (no images offline), breaking D-08's "indistinguishable" claim.
**How to avoid:** Prompts must not request `image` fields. Golden-path JSON contains no image URLs. Both live and cached paths render identically with no images.

### Pitfall 5: JSON import in api/ without resolveJsonModule
**What goes wrong:** `api/live.ts` does `import goldenPath from '../data/golden-path/demo-results.json'` — TypeScript compiler errors under `"moduleResolution": "bundler"` without `resolveJsonModule: true`.
**Why it happens:** Current `tsconfig.json` has no `resolveJsonModule` key. `bundler` resolution mode requires explicit opt-in for JSON.
**How to avoid:** Add `"resolveJsonModule": true` to `tsconfig.json` `compilerOptions`. Vite does not use this tsconfig for client code (Vite handles JSON natively); this only affects the TypeScript type-checking step for `api/` + `shared/`.

### Pitfall 6: web_search not enabled in Anthropic Console
**What goes wrong:** API call returns 400 or the tool silently doesn't fire (model answers from training knowledge). The capture script snapshots stale data.
**Why it happens:** Anthropic requires an org admin to enable web_search in the Claude Console before API access. [CITED: platform.claude.com/docs/en/docs/build-with-claude/tool-use/web-search-tool]
**Warning signs:** `usage.server_tool_use.web_search_requests === 0` in the response. Listings look like generic/generic "example" entries. Capture script returns `fromCache: false` but items don't look current.

### Pitfall 7: dayinlife items rendered through array path
**What goes wrong:** `AIList` for `dayinlife` renders with `renderItem={(text) => <p>...</p>}` — this works only when `data` is a string. If the proxy returns an array (wrong prompt output), the `Array.isArray(data)` branch fires and `renderItem` is called with individual characters instead of the narrative.
**How to avoid:** Validation guard explicitly checks `typeof raw === 'string'` for `dayinlife` and throws otherwise. Test with a fixture in vitest.

## Code Examples

### Complete api/live.ts skeleton
```typescript
// Source: follows api/health.ts pattern [VERIFIED: codebase read]
// + web_search call [CITED: platform.claude.com web-search-tool docs]
import type { VercelRequest, VercelResponse } from '@vercel/node';
import type { LiveDataRequest, LiveDataResponse, LiveCategory } from '../shared/types';
import Anthropic from '@anthropic-ai/sdk';
import goldenPath from '../data/golden-path/demo-results.json'; // requires resolveJsonModule: true in tsconfig.json

const client = new Anthropic(); // reads ANTHROPIC_API_KEY from process.env

// cityName is the full "City, ST"/"City, Country" string (e.g. "Lisbon, Portugal").
// web_search user_location.country wants an ISO 3166 alpha-2 code; derive it from the suffix.
const COUNTRY_BY_SUFFIX: Record<string, string> = { Portugal: 'PT', UK: 'GB', Germany: 'DE', Canada: 'CA' };
function countryFor(cityName: string): string {
  const suffix = cityName.split(', ').pop() ?? '';
  return COUNTRY_BY_SUFFIX[suffix] ?? 'US'; // US cities end in a 2-letter state code -> default US
}

export default async function handler(req: VercelRequest, res: VercelResponse): Promise<void> {
  if (req.method !== 'POST') { res.status(405).json({ error: 'Method not allowed' }); return; }
  const { category, cityName, profession, age } = req.body as LiveDataRequest;

  const serve = (items: unknown, fromCache: boolean) => {
    const payload: LiveDataResponse = { category, cityName, fromCache, items };
    res.status(200).json(payload);
  };

  try {
    const msg = await client.messages.create({
      model: 'claude-sonnet-4-6',
      max_tokens: 2048,  // 1024 is too low: JSON truncation → parse failure → always cache (defeats D-04)
      system: 'You are a data assistant. After searching the web, output ONLY a JSON block. No prose outside the block. Format: ```json\\n[...]\\n```',
      messages: [{ role: 'user', content: buildPrompt(category, cityName, profession, age) }],
      tools: [{
        type: 'web_search_20250305',
        name: 'web_search',
        max_uses: 3,
        // country: ISO alpha-2 derived from the cityName suffix. Do NOT use `cityName === 'Lisbon'`
        // — the runtime value is "Lisbon, Portugal" so that is always false. Map the suffix after ", ":
        //   { Portugal:'PT', UK:'GB', Germany:'DE', Canada:'CA' }, default 'US' (US cities end in a state code).
        user_location: { type: 'approximate', city: cityName, country: countryFor(cityName) },
      }],
    });

    const text = msg.content.filter(b => b.type === 'text').map(b => (b as Anthropic.TextBlock).text).join('');
    const fenced = text.match(/```(?:json)?\s*([\s\S]*?)```/);
    const raw = JSON.parse(fenced ? fenced[1].trim() : text.trim());
    const items = validateItems(category, raw); // throws on bad shape → catch → golden path
    serve(items, false);
  } catch {
    // cityName is the FULL "City, ST" string, matching the golden-path keys ("Austin, TX") — no stripping.
    const fallback = (goldenPath as Record<string, Record<string, unknown>>)[category]?.[cityName] ?? [];
    serve(fallback, true);
  }
}
```

### Client-side fetch with parallel fan-out (D-04 / D-05)
```javascript
// Source: PotentialApp.jsx pattern, modified for D-04 button + D-05 parallel
import goldenPath from '../../data/golden-path/demo-results.json';

function handlePullLiveData(selectedCity, profile, setCityAIData, setAiLoading) {
  const housing = profile.housing === 'rent' ? 'housing_rent' : 'housing_buy';
  [('jobs', housing, 'dayinlife')].forEach(cat => {
    const key = `${selectedCity.name}_${cat}`;
    setAiLoading(prev => ({ ...prev, [key]: true }));
    const controller = new AbortController();
    const tid = setTimeout(() => controller.abort(), 20_000);
    fetch('/api/live', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ category: cat, cityName: selectedCity.name, profession: profile.profession }),
      signal: controller.signal,
    })
      .then(r => { if (!r.ok) throw new Error(`HTTP ${r.status}`); return r.json(); })
      .then(data => setCityAIData(prev => ({ ...prev, [key]: data.items })))
      .catch(() => {
        const fallback = goldenPath[cat]?.[selectedCity.name];
        setCityAIData(prev => ({ ...prev, [key]: fallback ?? 'error' }));
      })
      .finally(() => {
        clearTimeout(tid);
        setAiLoading(prev => ({ ...prev, [key]: false }));
      });
  });
}
```
